# 产品需求翻译 Skill

## 调用方式

当用户用模糊语言描述产品需求时，激活此流程。**不要直接写代码**，先帮用户把需求理清。

## 工作流程

### 第1步：需求体检（每次最多问3个，2-3轮结束）

**产品定位：**
1. 这个功能/产品是给谁用的？（用户画像）
2. 用户从哪进来的？（渠道→触点→转化）
3. 用户做之前是什么状态？做完后得到了什么？

**功能边界：**
4. 这个功能的最简版能砍到什么程度？
5. 什么东西 **现在明确不做**？
6. 如果只能做一件事，先做哪件？

**交互路径：**
7. 用户点击第一下之后，跳到哪里？
8. 如果用户中途退出，下次回来看到什么？
9. 出错时（支付失败/断网/数据异常）用户看到什么？

**数据与交付：**
10. 用户付了钱/提交信息后，怎么得到服务？（自动？人工？）

### 第2步：输出结构化需求文档

```markdown
## 需求：[一句话标题]

### 用户故事
- 作为 [谁]
- 我想 [做什么]
- 以便 [得到什么价值]

### 核心路径（Happy Path）
1. 用户打开 [页面]，看到 [内容]
2. 用户点击 [按钮]，跳转到 [页面]
3. 用户在 [页面] 填写 [信息]
4. 用户点击 [按钮] 完成 [操作]
5. 系统返回 [结果]，用户看到 [页面]

### 边界与异常
- [异常情况A] → 用户看到 [处理方式A]
- [异常情况B] → 用户看到 [处理方式B]

### 前端需求
- [页面名] 页面：
  - [组件/字段]
  - [交互行为]

### 后端需求
- `[方法] [API路径]`：接收 [参数]，返回 [数据结构]
- 数据校验：[规则]
- 错误码：[code] → [msg]

### 明确不做（本期）
- [排除项]

### 验收标准
- [ ] [可验证的结果]
```

### 第3步：任务拆解

```markdown
## 执行任务

### 后端
- [ ] 文件 [路径]：[操作]

### 前端
- [ ] 文件 [路径]：[操作]

### 配置
- [ ] [路由/权限/数据库]
```

## 核心原则

- **宁少勿多**：能跑的 MVP > 功能齐全但未上线
- **先问后做**：不确定的地方问用户，不猜
- **说人话**：输出给用户看的部分不要有技术术语
- **可执行**：需求文档必须能被另一个 Claude 直接用来写代码
