# 产品需求翻译 Skill

## 调用方式

当用户用模糊语言描述产品需求时，激活此 Skill。不要直接写代码，先帮用户把需求理清。

## 工作流程

### 第1步：需求体检（问10个核心问题）

根据用户描述的模糊需求，从以下问题库中选最相关的问题，**一次最多问3个**，来回2-3轮即可：

**产品定位：**
1. 这个功能/产品是给谁用的？（用户画像）
2. 用户从哪进来的？（广告→私域→小程序？还是直接搜索？）
3. 用户做这件事之前是什么状态？做完之后得到了什么？

**功能边界：**
4. 这个功能的最简版是什么？（砍掉一切非必要）
5. 什么东西 **现在不做**？（明确排除清单）
6. 如果只能做一件事，先做哪件？

**交互路径：**
7. 用户点完第一下之后，跳到哪里？
8. 如果用户半路退出了，下次回来应该看到什么？
9. 出错的时候（比如支付失败、网络断了），用户看到什么？

**数据与交付：**
10. 用户付了钱/提交了信息之后，怎么得到服务？（自动下发？人工联系？）

### 第2步：输出结构化需求文档

用以下固定格式输出，确保任何技术 Claude 都能直接执行：

```markdown
## 需求：[一句话标题]

### 用户故事
- 作为 [谁]
- 我想 [做什么]
- 以便 [得到什么价值]

### 核心路径（Happy Path）
1. 用户打开 [页面]，看到 [内容]
2. 用户点击 [按钮]，跳转到 [页面]
3. 用户在 [页面] 填写 [信息]
4. 用户点击 [按钮] 完成 [操作]
5. 系统返回 [结果]，用户看到 [页面]

### 边界与异常
- 如果 [异常情况A]：用户看到 [处理方式A]
- 如果 [异常情况B]：用户看到 [处理方式B]

### 前端需求
- [页面名] 页面需要展示：
  - [字段/组件1]
  - [字段/组件2]
- [按钮/交互] 触发 [行为]

### 后端需求
- [方法] [API路径]：接收 [参数]，返回 [数据结构]
- 数据校验：[校验规则]
- 错误处理：[错误码] → [错误信息]

### 明确不做（本期）
- [排除项1]
- [排除项2]

### 验收标准
- [ ] 用户能 [操作A] 看到 [结果A]
- [ ] 当 [异常B] 时，用户看到 [预期B]
```

### 第3步：生成任务拆分

需求文档确认后，拆成 Claude 可执行的任务列表：

```markdown
## 执行任务拆解

### 任务1：后端 [模块名] — 预计X个文件
- [ ] 在 [文件路径] 中 [具体操作]
- [ ] 注册路由 [路径] → [方法]

### 任务2：前端 [页面名] — 预计X个文件
- [ ] 在 [文件路径] 中 [具体操作]
- [ ] 在 pages.json 注册新页面

### 任务3：测试验证
- [ ] curl 测试 [接口]
- [ ] 检查 [边界场景]
```

## 核心原则

- **宁少勿多**：第一期能跑的版本 > 功能齐全但没上线
- **先问后做**：不确定的地方问用户，不要自己猜
- **说人话**：输出给用户看的部分不要有技术术语
- **可执行**：输出的需求文档必须能被另一个 Claude 直接拿来写代码
